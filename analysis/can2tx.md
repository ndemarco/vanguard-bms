# CAN transmit frames (29-bit IDs, J1939 style, source address 0xF3, 500 kbit/s)

Scope: every frame the firmware queues on CAN through the TX struct at RAM 0x17A2. All frames are extended-ID, DLC 8, data frames, sent unsolicited (no RTR, no request/response PGN handling) except the three reply frames 0x18FF50F3 / 0x18FF51F3 / 0x18FF52F3 that are tied to the receive commands in sections/cmd.md.
Tags: CONFIRMED = read directly from code. INFERRED = reasoned from usage. "wa" = program word address (Ghidra rom: space, same as out2/listing.txt). Variable meanings are in sections/glossary_can2tx.md (and sections/glossary_cmd.md for command-related RAM).

## 0. How the frames are produced (CONFIRMED)

* Struct at RAM 0x17A2: [17A2] = ID low 16 bits (PS<<8 | SA), [17A4] = ID bits 28..16, [17A6] = 3 (0x03 or 0x02: both mean "extended", only value 4 means standard; FUN_rom_00f19c wa 00f19c), [17A8] = DLC (always 8), [17A9..17B0] = data byte 0..7.
* Queue call FUN_rom_00EDD8(prio, &0x17A2) copies the struct into the first free CAN TX buffer (buffers 0..7, DMA RAM 0x2200 + 16*n) and sets the buffer priority field TXnPRI = prio & 3 (wa 00edd8). FUN_rom_00EDA8 then requests transmission. prio 1 = "low intermediate", prio 0 = "lowest". When more than one buffer is waiting, higher priority buffers go first, so the priority-1 frames overtake the priority-0 frames. If all 8 buffers are busy the frame is silently dropped (return value ignored).
* The periodic frames are all generated by one scheduler, FUN_rom_0093D6 (wa 0093d6..009fc8), called from the main loop FUN_rom_0086FA (call at wa 0089ba) whenever at least 2 ticks of 0x1664 passed since the previous call ("0x1664 - 0x16b0 >= 2"; the same pass then also runs the CAN11 sender FUN_rom_009fd0). The scheduler is one nested if/else chain: it walks the list below in order, and at the FIRST frame whose timer has expired it builds and queues that single frame and returns. So at most one periodic frame is queued per call (nominally every 2 ms), and when several are due at once they go out in list order, 2 ms apart.
* A frame is due when (0x1664 - lastSentStamp) >= period, with an unsigned 16-bit subtraction (wa 0094c8 etc: "sub W3,W2 ; compare ; bra leu skip"). The stamp is set to the current tick at the moment of queuing. Real period = nominal period plus 0-2 ms of scheduling delay plus queueing delay (up to ~27 x 2 ms = 54 ms for a late list entry when many frames are due together, e.g. just after start-up, because all stamps are initialised to the same tick by FUN_rom_008AF4).
* 0x1664 is a 1 ms tick: Timer1 PR1 = 0x0EA6 (3750), T1CON = 0x8010 (prescaler 1:8), Fcy = 30 MHz (CLKDIV 0x3102, PLLFBD 0x1C, 16 MHz crystal assumed): 3750 * 8 / 30 MHz = 1.000 ms. FUN_rom_010E86 increments it in the Timer1 interrupt. CONFIRMED apart from the crystal assumption.
* The hold-off counter 0x17D0 in front of the chain is never set non-zero by any code, so it does not delay anything (wa 0093d6 entry, FUN_rom_008af4).
* There is no start-up delay table: all stamps equal the tick at power-up/re-init, so the first copy of each periodic frame is sent one full period after start-up (exception list in section 3).
* Not sent during the sleep/standby loop FUN_rom_006142 except the two one-shot frames 0x18FF08F3 and 0x0CF096F3 (FUN_rom_005C70).
* Numbers: all multi-byte fields are little endian unless a row says "big endian". Float-to-integer conversions are truncation toward zero (FUN_rom_00062C signed, FUN_rom_00066E unsigned with negative values clamped to 0, wa 00062c / 00066e), and the CAN field keeps the low 16 bits of the result.
* Temperature byte convention: byte = degrees C + 40, 0 = no valid reading (CONFIRMED: FUN_rom_00add0 / FUN_rom_00b22a compute "byte - 0x28" and clamp to -40..+70 C).
* Current convention used by the frames that carry current: raw16 = mA / 50 + 32000, i.e. 0.05 A per bit with offset 32000 (= -1600 A); the exact formula is trunc(current_mA / 50.0 + 32000.0) with float constants 0x42480000 (50.0) and 0x46FA0000 (32000.0) (wa 009498..0094a4). Positive = charging (INFERRED from the sign of the protection thresholds table[0x98] = -900000, table[0xb0] = +300000 compared against the same value in FUN_rom_00cb6e).
* Voltage convention for cell and pack voltage: mV (cells) and 0.05 V per bit (pack voltage in 0x0CF090F3 / 0x0CF095F3 = mV / 50).

### 2.3 0x0CF094F3 - current limits and SOC (100 ms)  [wa 009536..0095da]

Firmware defect: bytes 0..3 are written to RAM 0x1789..0x178C (the CAN11 TX struct) instead of 0x17A9..0x17AC (wa 009562, 00956a, 00958c, 009594: "mov.b wreg,0x1789 / 0x178a / 0x178b / 0x178c"). ### 2.23 0x18FF50F3 - log status / CAN11 error report (priority 0)

One ID, two families of payload:

(a) Event-log status (FUN_rom_00abce, wa 00abce): sent every 500 ms when no other periodic frame is due (wa 009fc4), after every event-log write (call at wa 00c280 inside the log writer), once at boot (wa 00873c, main-loop start) and as the acknowledge of RX command 0xC7 (wa 008f68). Bytes: 0-3 log write pointer 0x1B78:0x1B76 BIG endian (byte 0 = high byte of 0x1B78), 4 = verify status 0x1B92, 5-6 = log write count 0x16BE BIG endian, 7 = last event code 0x16BC. Full description and event codes in sections/cmd.md section 2.2. CONFIRMED.

(b) CAN11 bus fault reports, sent on CAN by the CAN11 interrupt handler FUN_rom_00030E (wa 00030e, reads C1INTF at RAM 0x048A) and by the CAN11 receive routine FUN_rom_00E106 (wa 00e118); DLC 8, every byte follows a repeating pattern:

| Data bytes | Trigger | Sender wa | Tag |
|---|---|---|---|
| 01 00 01 00 01 00 01 00 | CAN11 interrupt, error flag set and C1INTF.TXBO (0x2000, bus off) | 00ab10 | CONFIRMED |
| 02 02 02 02 02 02 02 02 | C1INTF.TXBP (0x1000, transmit bus passive) | 00ab4a | CONFIRMED |
| 01 02 01 02 01 02 01 02 | C1INTF.RXBP (0x0800, receive bus passive) | 00ab8c | CONFIRMED |
| 01 01 01 01 01 01 01 01 | C1INTF.RBOVIF (0x0004, receive-buffer overflow); CAN11 is then re-initialised (FUN_rom_00de28) | 00aac4 | CONFIRMED |

A receiver tells (b) from (a) only by content: the (b) patterns repeat one or two byte values across all 8 bytes, which a valid (a) frame (flash pointer, status, counter, event code) practically never does. There is no flag byte distinguishing them (open question 11).

### 2.25 0x18FF52F3 - log record dump (reply to RX cmd 0xCB, then stream)  [wa 0090f8, 008a64]

## 3. Conditional and event-driven senders

Everything in section 1 rows 1-26 is gated only by its timer, with these exceptions and conditions (CONFIRMED unless noted):

1. No periodic frame is sent while the main loop is not running: during the sleep loop FUN_rom_006142 only the one-shots below go out. Timers restart in FUN_rom_008af4 (called at the end of the start-up routine FUN_rom_005ef6), so every periodic frame appears for the first time one period after start-up.
2. 0x18FF08F3 and 0x0CF096F3 also go out once at each pass of the shut-down/sleep routine FUN_rom_005C70 (wa 005c70..005e00; reached through FUN_rom_006142, called at wa 0057a8, 00873a, 008868, 0088ba, 0088e4), immediately, regardless of the timers. The routine repeats on each wake-up pass of the sleep loop (loop test on RB6 in FUN_rom_006142). In that copy bytes 0-1 of 0x18FF08F3 are zero.
3. 0x0CF096F3 is also sent immediately (FUN_rom_00ac32, wa 00ac32) when cell balancing ends: from FUN_rom_00fa2e (wa 00fa38; clears the monitor-chip balance registers; called by FUN_rom_010a54 when no cell needs balancing and from wa 0063be) and from the acquisition state machine FUN_rom_0062EC (call at wa 0063c8) when balancing was active and the enable bit (RAM 0x161C bit 4) or the request bits (0x161B bits 0-1; copies of CAN11 0x105 data[1] and data[0]) are no longer set. Balancing itself: FUN_rom_010972 selects cells above the floor (default 3800 mV) whose spread above the minimum cell exceeds the start spread (default 40 mV; stop spread 10 mV); it runs only while the enable and request bits are set.
4. 0x18FF50F3 (a): additional sends after each log write (FUN_rom_00c10c end), at boot, and as acknowledge of RX command 0xC7. (b) CAN11 error events listed in 2.23, no time limit: each error interrupt sends one frame.
5. 0x18FF51F3 only after RX command 0xC9 on 0x0CFF00F3. 0x18FF52F3 only after RX command 0xCB (not while 0x17F9 != 0, i.e. not while a solenoid driver is on; the stream pauses while a driver is active and is aborted by a new 0xCB or after frame 36).
6. 0x18FF50F3 (a) periodic copy has the lowest priority in the scheduler chain: it is only sent when ALL other 26 periodic timers are not due (wa 009fb0..009fc6), which in practice is about every 500 ms because the other frames are due on a 100 ms / 500 ms grid.
7. Data validity (INFERRED): a failed monitor-chip acquisition sets fault bit 0x1000 (section 4); the frames keep being sent with the last values (no validity flag in any frame). Temperature bytes of a failed sensor read 0 (excluded from max/min/mean, CONFIRMED); fewer than 12 valid sensors raises warning 0x0002 (CONFIRMED).
8. The set of senders is the same in every operating mode; no frame is only sent while charging. Only the CONTENT changes (mode code, limits, balancing mask).

## 5. Driver notes

* Key on the full 29-bit ID. 0x18FF06F3 (cell 13/14) and 0x0CFF06F3 (SOC) share PGN 0xFF06; 0x0CF096F3 is neither a request PGN nor addressed.
* Nothing is ever requested by PGN: no RTR, no PGN 0xEA00 request handling in the transmit side. A listener only needs to receive.
* Recommended decode: cell mV direct; temperature degC = byte - 40; current A = (raw - 32000) * 0.05; pack voltage V = raw * 0.05 (0x0CF090F3 bytes 4-5 and 0x0CF095F3), or sum of cells / 1000; SOC % = SOC percent field (0x0CFF06F3) or raw / 640 (0x0CF094F3).
* Ignore 0x0CF094F3 bytes 0-3.
* The cell-voltage group frames have no sequence or validity byte; use the cell-sum in 0x0CFF32F3 or 0x0CF090F3 to cross-check.

## 6. Open questions

1. ADC calibration constant RAM 0x1CC2 (divisor of the two ADC voltages 0x17EC / 0x17F0 in 0x0CFF32F3 and 0x0CF095F3) has no writer in the image and is not in the start-up data-init template (template at program word 0x14E8C covers 0x163E, 0x1722, 0x1800, 0x1A00, 0x1030, 0x1036, 0x103A, 0x1000 only). Its value is therefore unknown; the formula is mV = 58000 * adc_avg / 0x1CC2. If the constant is the 12-bit full scale (4095) the range is 0..58 V.
2. Crystal frequency (16 MHz assumed) decides the 1 ms tick and every period in this document.
3. Unit and meaning of the capacity numbers (0x1C0A, 0x1BFE, table[0xD8], table[0x118], 0x1748): 0.01 Ah is consistent with the cell counts, but not proven.
4. Whether 0x1BB4 is the discharge limit and 0x1BD2 the charge limit (reasoned from the sign of the current used by each function) - and since 0x0CF094F3 bytes 0-3 are broken, the limits are never visible on CAN anyway (they are on CAN11 0x113/0x114, see CAN11 section).
5. Function of the digital inputs RB11, RB12, RB13, RB14 (0x0CF096F3 byte 6) and of the outputs behind LATA3, LATA4, LATD3 (byte 7 bits 1-3).
6. Meaning of 0x18FF30F3 constant data CD E9 02 93 4A 00 00 00.
7. Meaning of table[0xE8], table[0xE4], table[0xF4] values sent in 0x0CFF3EF3.
8. Exact meaning of the SOH-related values (0x0CFF33 / 34 / 35) and the learned-capacity unit.
9. Whether all PGN numbers 0xF090..0xF10A correspond to a published profile.
11. 0x18FF50F3 carries both the log status and the CAN11 error patterns with no discriminator byte.
10. Latency under load: the scheduler can delay the last list entries by tens of ms right after power-up; steady-state spacing was not measured on hardware.
